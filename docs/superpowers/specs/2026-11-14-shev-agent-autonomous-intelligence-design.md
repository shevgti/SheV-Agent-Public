# SheV Agent: самостоятельный ИИ-помощник — проектное решение

## Цель

Превратить SheV Agent из локального чата с ограниченным набором функций и генератора Markdown-паспортов в универсального помощника, который понимает поручение, исследует его в интернете, проектирует нужные инструменты и специалистов, выполняет разрешённые действия, проверяет результат и сохраняет полезные навыки.

Пользователь общается с главным чатом обычным русским языком. Ему не требуется вручную выбирать API, писать системные инструкции или связывать инструменты.

## Что пользователь должен получить

Пример: «Создай агента, который ищет прогноз погоды для любого города».

Главный агент должен:
1. Понять цель и критерии успешной работы.
2. Найти актуальные источники и сервисы в интернете.
3. Открыть и прочитать документацию, сравнить API и ограничения.
4. Выбрать подходящий способ получения данных и объяснить выбор.
5. Сформировать исполняемую конфигурацию специалиста, а не только Markdown-паспорт.
6. Назначить ему только реально зарегистрированные инструменты и необходимые разрешения.
7. Проверить конфигурацию, выполнить тестовые запросы и проверить фактические результаты.
8. Сохранить специалиста и полезный навык в локальной библиотеке.
9. Сделать специалиста доступным из главного чата и показать понятный отчёт.

## Текущее состояние проекта и ограничения

В ветке `feat/integrated-agent-execution` уже присутствуют:
- ADK-координатор и специалисты researcher/planner/engineer/reviewer;
- интеграции провайдеров локальной и облачных моделей;
- `PublicWebSearchTool`, который сейчас выполняет ограниченный read-only поиск через DuckDuckGo и возвращает сниппеты;
- `OpenMeteoWeatherTool`;
- `AgentToolRegistry`, `AgentToolExecutor`, `CapabilityPolicy` и декларативные разрешения;
- валидатор планов, последовательный `AgentPlanExecutionEngine`, allowlist инструментов и проверки подтверждения;
- генератор `AgentManifest`, который пока создаёт безопасный черновик, а не активного исполняемого агента.

Критические незавершённые части:
- главный чат не имеет общего надёжного цикла «план → вызов инструмента → результат → следующая мысль → проверка» для всех поддерживаемых провайдеров;
- текущий публичный поиск не открывает и не извлекает содержимое страниц, не является Google Search и не даёт полноценной браузерной навигации;
- созданные специалисты не получают реальный набор разрешённых инструментов: `AgentRunPolicy` пока блокирует специалистов с инструментами;
- нет законченного процесса исследования, проектирования, проверки и активации нового инструмента/навыка;
- необходимо проверить сохранение памяти/навыков и продолжение многошаговых задач после перезапуска приложения.

## Предлагаемая архитектура

### 1. Единый интеллектуальный координатор

Главный чат использует выбранную пользователем облачную модель (OpenAI, Gemini, OpenRouter или Codex — если провайдер подключён и поддерживает нужный режим) для сложных задач и локальную модель как доступный fallback. Приложение не обещает одинаковое качество моделей и не пытается копировать закрытые веса ChatGPT.

Для каждого провайдера нужен общий контракт возможностей: текст, контекст, вызов инструментов, потоковый ответ, лимиты, отмена, ошибки. Если провайдер не поддерживает tool/function calling, приложение должно использовать явный совместимый цикл выполнения или сообщать об ограничении, а не симулировать вызовы.

### 2. Планирование и исполнение

Координатор должен уметь:
- разбивать задачу на шаги и зависимости;
- выбирать подходящие инструменты из каталога;
- проверять наличие обработчика и разрешения до исполнения;
- выполнять шаги по одному, передавать результаты обратно модели;
- пересматривать план после ошибок;
- проверять постусловия независимым способом;
- сохранять прогресс, события и артефакты;
- честно сообщать, что сделано, что не удалось и что требует подтверждения.

Успешный ответ инструмента не считается доказательством завершения всей задачи.

### 3. Интернет-исследование и браузер

Построить read-only веб-контур:
- поисковый провайдер с поддержкой Google только через разрешённый/официальный доступ (например, настраиваемый Search API); не парсить Google SERP в обход условий сервиса;
- открытие URL только через проверенный HTTP(S)-клиент;
- извлечение основного текста страницы, заголовка, canonical URL и даты, когда она явно доступна;
- переход по ссылкам с ограничениями домена, редиректов, размера, времени и MIME-типа;
- загрузка файлов только в изолированную папку приложения с лимитом размера, проверкой типа и SHA-256;
- чтение PDF/текстовых/документационных файлов через безопасные парсеры;
- цитирование источников и различение сниппета, прочитанной страницы и проверенного факта.

Не предоставлять модели произвольный доступ к сокетам, локальной файловой системе или произвольным URL без проверки. Защита от SSRF, private/link-local IP, DNS rebinding, чрезмерных редиректов, HTML prompt injection и вредоносных файлов обязательна.

### 4. Динамические специалисты и навыки

Разделить:
- **паспорт** — описание цели и поведения;
- **навык** — проверенная инструкция/процедура с версиями, источниками и тестами;
- **инструмент** — конкретный типизированный handler с JSON Schema;
- **разрешение** — выданное пользователем право на конкретный класс операций;
- **агент** — конфигурация, объединяющая модель, инструкции, навыки, инструменты, память и лимиты.

Модель может самостоятельно предложить и спроектировать новые навыки/инструменты, но не может выдать себе права. Новый исполняемый код не запускается автоматически: сначала статический анализ, тесты в изоляции, просмотр diff и подтверждение пользователя. Предпочитать существующие проверенные API/инструменты вместо генерации кода.

### 5. Память и обучение на опыте

Это не переобучение весов модели. «Обучение» в приложении реализовать через:
- долговременную библиотеку навыков с версиями;
- память проекта и предпочтений;
- краткие итоги исследований и проверенные источники;
- примеры успешных/неуспешных выполнений;
- оценки и исправления пользователя;
- retrieval релевантного опыта в контекст следующей задачи.

Сохранять происхождение, дату, версию и статус проверки каждого навыка. Не сохранять секреты/API-ключи в prompt или обычные файлы.

### 6. Полномочия и подтверждения

Автономно разрешить:
- поиск, чтение публичных страниц и документации;
- анализ данных, локальные черновики и планы;
- загрузку безопасных документов в изолированное хранилище приложения;
- локальные тесты в ограниченной среде;
- создание и обновление черновиков навыков.

Всегда требовать отдельного подтверждения перед:
- установкой APK/приложений или запуском скачанного кода;
- изменением файлов проекта вне черновой песочницы;
- публикацией, отправкой сообщений или созданием внешних ресурсов;
- покупками, платежами, удалением/перезаписью данных;
- изменением разрешений, секретов и системных настроек.

Права задаются пользователем на уровне capability и конкретного действия; инструкции модели никогда не обходят policy.

## Подходы и выбор

1. **Только улучшить prompt локальной модели.** Быстро, но не добавит реального браузера, надёжного tool loop и качества рассуждения, которого модель не имеет. Не рекомендуется как основное решение.
2. **Универсальный runtime поверх подключённых моделей и типизированных инструментов.** Рекомендуется: использовать уже имеющиеся провайдеры, ADK, tool registry, capability policy и планировщик; добавить общий цикл вызова инструментов, веб-исследование, навыки и полноценный runtime специалистов. Даёт лучший баланс гибкости и контроля.
3. **Полностью автономный shell/браузер с произвольным выполнением кода.** Максимальная свобода, но слишком рискованно для Android-приложения и не требуется для большинства задач. Не выбирать.

## Этапы реализации

1. **Стабилизация текущей ветки:** проверить CI/сборку, интеграцию PR #44 и все уже существующие инструменты; не терять update pipeline.
2. **Интеллект главного чата:** унифицировать provider capabilities, контекст, планирование, tool-call loop, повторы/ошибки/отмену и проверку результата.
3. **Интернет-исследователь:** поиск, открытие страниц, извлечение текста, безопасные загрузки, источники и защита от prompt injection/SSRF.
4. **Рабочие специалисты:** per-agent tool allowlist, runtime с теми же инструментами и policy, маршрутизация из главного чата, статусы и журнал запусков.
5. **Мастер создания навыков/инструментов:** исследование → проект → безопасная сборка/проверка → тест → подтверждение → активация.
6. **Долговременная память навыков:** версии, источники, retrieval, обратная связь и восстановление после перезапуска.
7. **Полный приёмочный прогон на устройстве:** погодный агент, интернет-исследователь, создание нового безопасного навыка, ошибки сети/модели, отмена, перезапуск, запрет опасных действий.

## Критерии готовности

- На запрос о текущей погоде главный чат получает фактические данные из сети, называет город и время/источник данных, а не угадывает.
- По запросу создать агента координатор исследует источники, создаёт исполняемую конфигурацию, назначает реальные разрешённые инструменты и запускает тесты.
- Созданный специалист вызывается из главного чата без ручного выбора вкладки или отдельного запуска пользователем.
- Если модель/инструмент/сеть недоступны, приложение показывает точную причину и не заявляет об успехе.
- Специалист не может использовать инструмент вне своего allowlist или обходить capability policy.
- Навык сохраняется между перезапусками с версией, источником и результатом проверки.
- Скачанный код не исполняется без подтверждения; сетевой и файловый доступ ограничен.
- Все критические пути покрыты unit/integration tests; CI green; отдельная проверка на реальном Android-устройстве.

## Решения по умолчанию

- Язык интерфейса и общения — русский.
- Для сложных задач использовать наиболее подходящего подключённого облачного провайдера; локальная модель — fallback.
- Веб-доступ по умолчанию read-only.
- Новые инструменты/навыки остаются черновиками до проверки и подтверждения.
- Не удалять и не переписывать существующие рабочие модули без доказанной необходимости.
